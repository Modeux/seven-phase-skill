# 工具化檢討（2026-11-06）

範圍：10-23～11-06（14 天）。問題只有一個：agent 花多少力氣在重寫同樣的機械腳本。

## 量到什麼
- 7,949 支一次性腳本、13MB、約 25 小時模型生成（約佔生成時間 12%）。
- worktree 守衛擋 982 次、py-edit 守衛擋 345 次，大多是這些腳本的形狀（變數、命令替換、heredoc）。
- 跑閘 2,541 次，讀閘輸出 2,591 次：比值 1.0，每跑一次閘就多一回合去 grep 結果。
- tdd-guide 平均每顆寫 6.3 支非產品腳本（10KB，244 顆）。

重跑：`retros/2026-11-06-measure/mine3.py <天數> <輸出.jsonl>`，再 `analyze3.py <輸出.jsonl>`。

## 做了什麼（owner 選四組全做）
| 工具 | 取代 |
|---|---|
| `gate.py` | 手打 `go test`、`ng test`、`docker run`，加事後 grep |
| `mutate.py` | 手改檔、跑、手動還原的突變腳本 |
| `recv.py` | 主 session 收片時逐步手跑的機械檢查與 `merge_back` |
| `mkbrief.py` | 每包現寫的 `build_briefs*.sh` |
| `dbq.py`＋`scripts/fixtures/` | 手打 `docker exec psql`、現寫種子資料 |
| `walk_lib` 補 `at`／`tabOrder`／`net`／`scroll` | 走一趟腳本的重複樣板 |

判斷（紅的原因、偏離裁決、抽哪個突變）仍由主 session 做，工具只把它列成未做。

## 做的過程發現的
- 前端全專案 `ng test` 從來不是真綠：有 4 個名單內的 unhandled error，exit code 恆為 1，還有 3 支看分檔順序紅綠的測試。所以判準一直靠人逐名比對，也是工具第一版的盲點（名單只認測試名，全專案閘永遠 INCOMPLETE）。名單改成隨程式碼版控的 `known-red-*.txt`，工具自動比，訊息與來源都要對上才放行。
- 片可以把自己的失敗寫進名單來洗白，所以 `recv.py` 在片改過名單時改用快照那份。
- `extract.py` 行號越界、`rulesfor.py` 錯 root 兩個假綠，順手修掉並補測試。
