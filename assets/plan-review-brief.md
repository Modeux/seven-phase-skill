## 要找的五種問題
前三種是過去完整路包裡，第 6 階段才抓到、事後追到「本該在 PLAN 攔下」的主要形狀。
1. **狀態 × 事件矩陣少一列**：PLAN 新增或改動的每個非同步讀取、狀態欄位、按鈕、送出入口，列出它的狀態（未落地／在飛／失敗／空／到底／還有下一批…）和會打到它的事件（送出、重試、刪除、切換、卸載、別的入口寫入…），逐格問：PLAN 有沒有定義這格的行為？測試清單有沒有一支測這格？過去的例子：「清單空、但還有下一批」被畫成空態；「第一次讀取還沒成功就收到 201」；「按下的按鈕自己被換掉」，焦點掉到 body；「回合在飛時從籌碼送出」。
2. **先例與宣稱沒回程式碼核對**：PLAN 每一處「沿用 X」「同 X 的做法」「比照 X」，以及 PLAN 要寫的每條 INVARIANT／WHY，回快照確認 X 真的是那樣、前提在本包也成立。過去的例子：拿一個獨佔 slot 的 policy 當先例，套到共用斷路器的槽上；INVARIANT 只從 log 那側寫，沒對照另一個預設開啟的擷取開關；WHY 沿用「目的地在請求裡」，但新路徑的目的地不在請求裡。
3. **歸類跟既有規則矛盾**：PLAN 把某類驗證歸成「驗不到」「交給 UI lane／走一趟」「不做」，或宣稱某件事不必測的，對照 repo 的 `.claude/rules/`、子目錄 `CLAUDE.md` 和既有測試 pin。過去的例子：PLAN 寫「jsdom 驗不到焦點」，規則檔寫「jsdom 移除聚焦元素會退回 body，完全可測」。PLAN 的 `## 規則對照` 表是機械產生的命中清單：標「不相關」的每一份都要抽查理由是否成立；標「套用」的，確認那一節真的落成矩陣的一列或一支測試。
4. **檔案矩陣與呼叫者**：要改簽名／搬動／刪除的符號，有沒有呼叫者沒列進矩陣；同一波兩片寫同一檔（違反單一 writer）；手寫清單（INVARIANT 的路徑清單、白名單、多處對齊）在本包新增路徑後沒重走。
5. **SPEC → PLAN 漏項**：SPEC 的每條要求有沒有落到某一片和某一支測試；閘有沒有寫既存紅基線與判準。

不必報：風格、命名、切片粒度偏好、估時。

## 環境規則（違反會弄壞共用環境）
- **唯讀**：不得修改快照、主 checkout 任何檔案；禁 git commit／stash／checkout／apply／worktree 操作；Bash 用絕對路徑或 `-C`，不要 `cd`。交件方式見派工訊息（內部 lane：寫派工訊息給的報告檔；外審：直接輸出）。
- 還沒有程式碼改動，不必跑測試。<專案特有：例如禁在 host 跑會重建共用環境的指令>
- 不得連 prod DB、不得呼叫外部量測 API（額度與 prod 共用）、不得呼叫任何 LLM provider。不讀使用者對話內容、不印任何金鑰。
- graphify 只准查詢，不要 cd 到主 checkout：`graphify affected "<Func()>" --relation calls --graph <主 checkout 絕對路徑>/graphify-out/graph.json`（query 必帶 `--context call`）。

## 證據規則
- 註解、CLAUDE.md、SPEC、PLAN 都不是行為證據；行為只信程式碼本體。PLAN 對現況的描述跟程式碼不符＝finding。
- 任務書裡寫的任何「事實」都是待你否證的假設。

## 報告格式（報告全文照派工訊息的交件方式交；給主 session 的摘要 ≤15 行）
```
### [SEVERITY] 一句話標題
- 位置：PLAN 節名／D 編號／切片編號；牽涉程式碼時加 repo 相對路徑:行號（以快照為準）
- 證據：PLAN 原句＋程式碼片段或規則原句
- 失敗情境：照 PLAN 做完後，具體輸入／狀態 → 錯誤結果（或：哪一格沒有測試守住）
- 建議改法：改 PLAN 哪一節、加哪一列矩陣或哪一支測試；它處理哪一層（根因／緩解／症狀）
- 信心：高／中／低（低＝推論未驗證，說明缺哪一步驗證）
```
標題行照 `### [SEVERITY] 標題` 寫——收件時用腳本核對每一條都進了 PLAN 審查地圖。
SEVERITY ＝ CRITICAL（照做會資料遺失／靜默停擺／錢）、HIGH（照做會有明確 bug，或重要面沒有任何測試守住）、MEDIUM（邊界格沒定義或沒測、PLAN 對現況描述錯）、LOW（小問題）。
最後附一節「已查證無問題」：五種問題各一行，寫查了哪些、證據位置。
