## REVIEW.md 結構（依序；{{round_title}}一輪放一節，標題帶「{{round_title}}」）
1. `# {{slug}} — REVIEW（{{round_title}}）`，一段白話導言（3 行內：審查對象＝哪個快照／HEAD、幾路、零／幾條 CRITICAL；這份只是去重地圖，真假在第 7 階段收斂驗證）。
2. `## lane 配置`：表格 `lane｜agent｜鏡頭｜狀態`。agent 與鏡頭讀 `{{review_dir}}/tasks/<lane>.md` 首段；外審寫 CLI 與模型；狀態照上表（重跑、續接、空跑、換鏡頭替補都照實寫）。
3. `## 執行結果`：把 `{{index_md}}` 開頭的計數表**直接貼上**（不手數）。
4. `## 重點面結論`：表格 `F｜名稱｜結論（一句）｜主要證據 lane｜相關地圖列`，共用任務書的每個重點面一列（名稱照 brief.md）。結論只寫「有 N 列待驗」或「各路查過無發現（附哪幾路的『已查證無問題』）」，不下真假判斷。
5. `## 去重地圖`（標題必須含「去重地圖」四字）：
   - 表頭：`| 編號 | 宣稱嚴重度 | 一句話 | 位置 | 來源 | 備註 |`。
   - R1…＝合併後宣稱嚴重度 MEDIUM 以上（CRITICAL→HIGH→MEDIUM 排序，同級內依重點面順序），L1…＝LOW。編號不重複；同一份 REVIEW 多輪時每輪各自編號。
   - 「一句話」用白話寫具體失敗情境（誰、做什麼、看到什麼錯）。「位置」寫主要的 `path:line`（以快照為準，可多個，用「；」分隔）。
   - **「來源」格只寫條目 id**（`go#1, security#1, codex#2`，逗號分隔），不寫別的字；嚴重度分歧、合併理由、更正（例：perf#2 更正 db#2）放「備註」。主 session 手讀認可、沒照標題格式的報告，來源寫 lane 名不帶編號，例如 `grok(MEDIUM)`。
   - 宣稱嚴重度取各來源中最高者，備註註明分歧（例「go HIGH、grok CRITICAL」）。
   - 合併判準：同一根因、同一修法才併；症狀相似但根因／位置不同的分開列並在備註互指。**合錯比漏報更糟**，拿不準就分開。
   - 備註另寫：是否碰 owner 拍板項（寫「交 owner」）、是否預先登記、是否 HEAD 既存但本包擴大。
   - 表格後一行：`幾路同報`——列出來源 ≥2 條的地圖列（編號＋來源數）。
6. `## 未收錄`：每條一行 `- <lane>#<n>：<一句理由>`。intake gate：只有「嚴重技術債」或「潛在 bug 風險」（含跨層漂移、誤導性註解）才進地圖。擋下的：純審美／風格偏好；PLAN「不做清單」與「已知限制」裡的東西（除非報告證明本包讓它變糟）；共用任務書「已知既存紅」與已記 BACKLOG 或 `BACKLOG-archive.md` 的低項。**重複報同一件已在地圖的不算擋下**——併進那一列的來源格，不放這裡。拿不準就收進地圖、備註「intake 存疑」。
7. `## invariant 勘誤`：若有 lane 證明共用任務書或 PLAN 寫的某個「事實」是錯的，各列一行：哪句、錯在哪、證據 lane#n。沒有就寫「無」。
8. `## 給第 7 階段`：需要 owner 拍板的條目（R／L 編號＋一句問題），與需要驗證員優先驗的（信心中／低、各路說法矛盾的）。

## 規則
- 不判真假、不提修法優先序、不問 owner——那是第 7 階段。只做去重、合併、編號、歸類。
- 不重新審查、不加入報告裡沒有的新發現；核對位置時發現某路的位置或事實明顯錯（例：行號指錯函式），在備註寫出。
- 每句描述行為的話以報告原文為準，不要比報告說得更肯定。
- 寫完自己跑：`{{reviewcov_cmd}}`，要 exit 0；不是 0 就修 REVIEW.md 再跑。
