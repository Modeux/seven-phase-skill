# 第 3 階段：Interview

目標：以 SPEC 的方向決議為前提，問到決策樹每個分支都有結論。**不重問討論已定案的事項。**

套 `mattpocock-skills:grilling`，提問一律 AskUserQuestion。白話協議（判準：不熟本專案的工程師讀完要能直接作答，讀不懂就重寫）：
- 先兩三句日常語言交代脈絡（現在情況、為什麼要決定、選擇的實際差別），再問**一件事，一次一題**。
- 技術縮寫與專案黑話首次出現附一句白話解釋。
- 選項寫「選了會發生什麼」的完整敘述；推薦項排第一並附理由；關鍵對比用 preview 文字圖。
- 至少涵蓋技術實作／UI-UX／edge cases／取捨；**不問顯而易見的問題，要挖 owner 沒想到的困難點**。
- 細節層級的分歧同樣可以做丟棄式原型實測拍板，觸發條件與做法同 `phases/2-discuss.md` 第 3 步。

完成後完整規格**補進 SPEC.md（接在方向決議之後）**，每題留「決議＋理由」表列；涉 UI 必須有**可驗收的 UI/UX 條目**（畫面狀態、互動流程、無障礙要求）。

**改到持久化資料語義的包**（新表、改既有列的意義、換表或搬欄）：SPEC 加「資料語義表」，每張表一段——一列代表什麼、生命週期（何時建立、保留多久、何時刪）、全部寫入入口、讀者、只留伺服器不進 API 的欄位、每條不變式由哪一層守（DB constraint／trigger、service、UI）與出處（第 1 階段的政策出處；「無出處」的逐條用 AskUserQuestion 問 owner）。換表或搬欄時，舊表每個欄位守的規則逐條寫去向：帶過去，或刻意不要＋理由。**不寫 DDL、查詢規模與部署**，那是 PLAN 第 7、9 條。
- 為什麼不從 schema 起手：schema 是這張表推出來的結果。從 schema 起手，表會照想像中的實體長，不照要回答的查詢與要守的規則長；而真正貴的返工是行為還沒定就把列的粒度寫死（`character_voices` 建表隔天就從「每角色一列」改掛創作者）。
- 為什麼要列舊欄位去向：點數 v1.4 換表時新的 `subscription_plans` 沒帶 `message_retention_days`（舊語義「NULL 永久、free 7 天」），查詢改寫死 90 天、只清付費用戶，約半年後才在 backlog 發現。從新行為推 schema 一樣會漏掉舊表守著的規則（11-02 codex／grok 外審）。

**有交付參照原型的包（`phases/2-discuss.md` 第 3 步），SPEC 加「原型差異表」**，checkpoint 前完成：
- 派 `ui-lane-reviewer` 在真瀏覽器並排開原型與現況，逐畫面、逐狀態列出差異，連號 P1…，每列：原型、現況、處置。
- 處置預設「照做」；跟既有規則衝突的才標「衝突」：錢的透明度、離開的路、陪伴文案守則、代名詞規則、觸控 ≥44、iOS 輸入框 16px、要動後端的。衝突逐條用 AskUserQuestion 問；owner 選了「不照做」的改標「刻意不同：<理由>」。
- **不推薦子集**（例如「先做最大的幾條」）。範圍要縮，改這張表、問 owner。

走完整路但訪談題很少時，可與 owner 商量把 SPEC＋PLAN 合寫；整包都簡單的應在開工分流時就走精簡路（`phases/lean.md`）。審查路數照規模分級，不因任何精簡再縮。

→ Checkpoint。
