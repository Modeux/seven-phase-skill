# 跨任務檢討（不是第 8 階段）

目標：看最近一批任務，在**品質、花費、速度**三面各找出值得改的地方，衝突時照「品質 > 省錢 > 速度」判；同時結清以前流程改動的驗收。**只提案，owner 拍板後才改 skill。**

## 為什麼不是每個任務的第 8 階段
- 單一任務的檢討在第 7 階段「流出分析」已經做了（有證據才觸發：HIGH 以上、同類再現、上線才發現）。整包再自我檢討一次，就是寫計畫的那個 session 在替自己的計畫打分數，最不可信。
- 一個任務只是一筆樣本，歸納出來的規則容易以偏概全；流程本來就改得勤（10-05～10-17 改了 40 多次），每包再加一輪，規則只會長得更快。
- 10-17 第一次試跑，抓到最大的問題不在程式碼：5 筆流程驗收裡 2 筆的腳本放在 `tmp/` 被清掉、2 筆過了期限沒人跑。

## 何時跑
- owner 說「檢討」才跑。看板在上次檢討後記錄了滿 5 個任務時會提示；看到提示，就在下一次回報時跟 owner 提一句。
- 新 session、context 短的時候跑：三面的資料都在腳本與檔案裡，不需要延續任務對話。

## 步驟
1. **先結清驗收**：讀 `ACCEPTANCE.md`「待驗」，到期的逐列照指令跑，判「有用／部分有效／沒用／未達標／判不了」，移到「結案」並寫證據與處置。判「沒用」的改動提撤回；判不了的寫缺什麼、要怎麼補。
2. **品質**（以最近一批任務為範圍）：
   - 各任務 REVIEW.md／PROGRESS.md 的 `## 流出分析` 表：統計「本該攔的閘」落在哪一階段、哪一種缺口；其中**規則早就寫了卻沒套用**的另外數（這類加文字沒用，只能換成機械閘）。任務目錄刪了，從它的 `docs(prps)` commit 用 `git show <hash>:<path>` 取回。
   - 各路審查的獨家產出：`scripts/laneyield.py <slug>…`；跨包比較時看「獨家已確認」，不看總條數。
3. **花費**：`scripts/taskcost.py --all-worktrees --days N`（每個任務）、`scripts/agentcost.py --all-worktrees --days N`（每種 agent）、`scripts/claudemdcost.py --days N`（說明檔載入）、`scripts/board.py --docsize`（說明檔大小與上次檢討比）。
   - transcript 的 `output_tokens` 少算（見 `references/lanes.md`），比較時看回合數與 cache 讀寫，不看 output 金額。
4. **速度**：`scripts/wallclock.py --days N`（每種 agent 的牆鐘與時間花在哪）。
5. **提案最多 3 條**，每條都要有：
   - **證據**：上面量到的數字，附基線。
   - **層級**：處理的是根因、緩解，還是症狀（`.claude/rules/evidence-and-root-cause.md`）。
   - **一項刪除**：同時提一條可以刪掉、合併或撤回的規則、路數或檔案。不准只加不減。
   - **對品質的影響**：省錢或加速的提案，要說明為什麼不掉品質（例如「它報到的每一條別路都有報」）。
   - **驗收**：採用後要怎麼判斷有沒有用（到期日、指令、判準）。
6. **拍板**：AskUserQuestion，多選，推薦項排第一。
7. **落檔**：報告寫到 `retros/<日期>.md`（不放 `tmp/`）；`ACCEPTANCE.md`「檢討紀錄」加一列；每條採用的提案在「待驗」加一列；改了 skill 就在 `references/history.md` 加一列。

## 不要做的事
- 不把一次的心得寫進記憶（記憶只放工作流與進行中待辦；10-05 清點時 201 條裡 151 條從沒在別的 session 被打開過）。
- 不重做第 7 階段的流出分析；這裡只看跨任務的趨勢。
- 驗收指令不放 `tmp/`。
- 量不到的不要硬下結論：寫「缺量測」，並把「補量測腳本」當成下一輪的候選提案。
