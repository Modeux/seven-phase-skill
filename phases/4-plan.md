# 第 4 階段：Plan

目標：依 SPEC 寫 `PLAN.md`。**PLAN 未經 owner 核准前禁止寫任何實作碼。** 有 planner 類 agent 可委其起草（planner 沒有 Write：要它把全文分段回傳或改用有 Write 的 agent 落檔），主 session 審視整合後定稿。

**PLAN.md 是給人讀的，機器面放 `plan-appendix/`**：規則對照（`rules.md`）、矩陣的符號／行號／呼叫者（`matrix.md`）、測試整表與反例（`tests.md`，或沿用每片一檔）。腳本都讀 appendix（`reviewcov --plan-tests`、`mkbrief`、`rulesfor --check`、`planview`），審查材料包要連 appendix 一起給。PLAN.md 的儲存格 ≤60 字，長理由寫表格下方 `**D3 為什麼**：` 小節；checkpoint 前 `scripts/planview.py --check <slug>` 要 exit 0（圖閘＋「超過 300 字的行 ≤5」）。為什麼：三份 PLAN 量下來，超過 300 字的行有四到五成是機器產的規則對照（一節 27–43KB、單行 4,903 字），其次是把理由塞進儲存格的 §0 定案（最多 26KB）；owner 11-07：「主要是想讓 PLAN 跟 SPEC 更好讀」。

PLAN 必須有：
0. **給 owner 的一頁**（第一節）：做什麼／不做什麼各一句、一張圖（切片 wave 或狀態機）、要 owner 拍板的（連到 §0 的列）、最大風險一句、怎麼驗收一句。一個螢幕內；後面各節的內容不重抄，只連過去。
1. **§0 定案**：owner 拍板表、主 session 定案（D1…，標「審查可推翻，但要附理由」）、SPEC 文字更正。表格只放決議短句；理由超過 60 字寫表格下方 `**D3 為什麼**：` 小節。
2. **規模與審查路數**：預估正式碼行數、是否碰錢／權限／跨層不變式 → 小包或大包（SKILL.md「依規模分級」），列出第 6 階段要開的 lane。切成多個可各自部署的包時，每一刀寫換到什麼、包表加「驗證帳」欄（SKILL.md「規模閥門」）。
3. **垂直切片**：每步端到端可運行；切片總表含「wave」欄、併發後臨界路徑估時。**依要讀的檔案切**：兩片要讀的檔案大量重疊（同一套件、同一組呼叫者）就合成一片、一顆 agent；碰不同區域的才拆開。每開一顆 agent 都要重付初始 context 與子目錄 CLAUDE.md，同一任務裡 tdd agent 讀的程式碼約三成是別顆也讀過的。
   - **PLAN 至少一張 ```mermaid**：切片總表上方畫片與 wave 的依賴（`flowchart LR`，節點＝片號），或 PLAN 才出現的狀態機／跨層時序（例如 worker→WS→前端的三層復原）；SPEC 已畫的引用節名、不重畫。真的沒有可畫的寫一行 `無圖：<理由>`。checkpoint 前 `scripts/planview.py --check <slug>` 要 exit 0（與第 11 條的 `rulesfor.py --check` 一起跑）。為什麼見 `phases/3-interview.md`「圖先文後」。
4. **單一 writer 檔案矩陣**：同一波裡 `routes.go`／`wire.go`／`openapi.yaml`／`api.types.ts`／同一 Go 套件／同一 spec 檔／`db/queries`＋sqlc 生成碼只屬於一片。資料層（migration＋sqlc＋設定全鏈）通常自成第一波單線。PLAN.md 的矩陣只留三欄：片、檔案、writer（同檔兩片＝矩陣錯）。每片**要碰的符號、行號範圍、主要呼叫者**寫 `plan-appendix/matrix.md`、每片一節 `## <片號>`（第 1 階段查到的位置；寫時對每個要改簽名／搬動／刪除的符號重跑一次 `graphify affected "<Func()>" --relation calls`＋grep 取聯集——第 1 階段到第 4 階段之間 dev 可能已前進），這節逐字進任務包——tdd-guide 每回合重讀的 context 約四成是自己 Read／cat／grep 找程式碼。`openapi.yaml`（32k 行單檔、零外部 `$ref`）在 appendix 必列**path 字串與 schema 名＋行號**、要套用的既有 `*_openapi_test.go` pin（`pathBlock`／`schemaBlock`／`jsonTags` 反射比對），並明寫「只 `grep -n` 定位後 `Read` offset／limit，不整檔讀」。
5. **每片的測試清單**：每支測什麼、期望紅的原因；**紅的歸屬**（主寫或 agent 寫，見第 5 階段）；先 grep 全 repo 既有 pin，避免漏掉命名不同的連帶紅。測試寫成表格、第一欄是編號（T1、H1-14…）：PLAN 審查的處置要點名它（下面「PLAN 審查」第 5 條）。整表放 `plan-appendix/tests.md`（或沿用每片一檔）；PLAN.md 的測試節每片一行「幾支、測什麼」，不重列編號。
   - **跨狀態的規則列維度，不列格子**：同一條規則要在多個狀態或多個出口成立時（18+ 遮罩、下架、權限、按下後的焦點、誰能讀寫），不逐格寫測試列，改寫一張維度表，每列第一欄是編號：規則一句話、單一閘點（函式或型別；沒有就在這包新建，所有出口都經過它）、各維度的值與**取值來源**（enum、路由表、`pg_constraint`、元件清單這類活的來源，不是手抄清單）、出口清單、一支窮舉表測。只逐格列例外（預期結果跟規則不同的組合）。表測由程式產生組合，並斷言組合數等於維度值的乘積，防空集合全綠。列不出維度的（手感、LLM 輸出品質、兩個請求的交錯時序）照舊列情境。為什麼：10-19～11-04 的 77 列流出分析約 77% 指向 PLAN（基線 79%），PLAN 審查、規則對照、點名測試加上去後沒有下降；事後任何 bug 都能說「矩陣該列」，靠人列舉狀態組合本來就列不完。這 77 列有 48 列落成機械閘，常見形狀是單一判斷點加窮舉表測（`mergeHistoryHead`、`resolveFaceAndReaction`）。
   - SPEC 有原型差異表的：每個「照做」列對到負責的片與驗收方式（走一趟步驟或測試編號），P 編號一個不漏。
6. **閘**：受影響包的 build／vet／單元＋具名整合（每片；前端片＝該 project 的 `ng test` 整包，見 `phases/5-implement.md`「主親跑閘」）；全閘（整合全包、lint、audit、前端整包＋production build、契約 lint）只在第 5 階段末與第 7 階段末各跑一次。寫出每個閘的既存紅基線與判準（「不新增」而非「全綠」）。
7. **風險與回滾**（含混版部署時序）、**部署後驗收**、**不做清單**（列在這裡的東西第 6 階段不算缺陷）。
   - **高風險 migration**（改既有列的意義、刪或改名欄位、backfill、舊版 gateway 讀新 schema 會出錯、可能長時間鎖表）逐步寫：新舊版相容（舊 gateway 對上新 schema 會怎樣）、部署順序（`DROP COLUMN` 先上不再讀該欄的 gateway 再 migrate，`.claude/rules/gateway/migrations-sqlc.md`）、資料能不能重建（有損 Down 的登記或守門，`db/CLAUDE.md` §Migration）、該表是否已上正式環境。已上線才拆 expand/contract；未上線可以一支 migration，Down 會丟什麼寫在檔頭。不另設 checkpoint、不另派審查（大包的 PLAN 審查本來就讀這節）。為什麼：第 4 條的「資料層第一波」是寫碼順序，不是部署順序；要不要分階段看相容性與能否重建，不看變更種類（11-02 codex／grok 外審）。
   - **改全站時限、retry、斷路器或連線池的包**，加一張「既有失敗路徑對照表」，每條路徑一列：路徑（檔案與符號）、新錯誤到達時 ctx 還活著嗎、錯誤被分類成什麼（重試／跳過／當結論）、改動前後的結果與發生窗、處置（本包修／BACKLOG／接受）。路徑清單來自 graph＋grep 的呼叫點，寫入、扣款、終局標記優先，不憑印象挑。「不是本包獨有」「本來就一樣壞」不算結論，要寫出前後差多少。為什麼：db-statement-timeout 的 R4（鎖前已 commit 的回合，走到不退費路徑的持鎖時間從約 15 分鐘變約 3 分鐘）與 R5（語句上限切斷扣款時 ctx 還活著，有錢的使用者被記成餘額不足）都被研究裡一句總括帶過，第 6 階段才攔到。
8. **本任務用到的 skills／MCP／agents 清單**與各自用途、使用時機。
9. 範圍面：沒有讀者的表不單獨先建，與第一個讀者同批做。新的旗標、後台設定、狀態與表一樣：寫誰寫入、誰強制執行，只顯示不算；對不上的不建。schema 在這裡才定：有 SPEC「資料語義表」的包，每張新表或改了意義的表寫一列——寫入入口、讀者與查詢（含基數與分頁）、不投影欄位、由此得到的欄位與約束。不投影欄位不進 `openapi.yaml`／`api.types.ts`，用投影測試釘住（例：`pair_journeys.twist_used` 在扣費前就寫成 true，`TestJourneyProjection_DoesNotCarryTwistUsed` 擋它出 API）。
10. **刪除／重構／新模組的圖查核**（根 CLAUDE.md §graphify）：PLAN 要刪除、合併或改簽名的每個符號先 `graphify query "<symbol>" --context call --budget 1500`；在 `graphify-out/GRAPH_REPORT.md` god-nodes 表內、或 dependents >3 的，列進 §0 定案附 dependents 清單，owner 核准 PLAN 才算確認，沒列的不得在第 5 階段順手移除。新增模組／helper 前先 `graphify query "<行為關鍵詞>"` 找既有等價物（規則的 WHY 在節點 `rationale` 屬性），找到就重用、找不到在 PLAN 寫一句「查過：無等價物」。
11. **規則對照**（每個完整路的包都要，不分大小）：把第 4 條檔案矩陣的路徑（含新檔、spec、`.html`）交給 `scripts/rulesfor.py <路徑…> >> .claude/PRPs/plans/<slug>/plan-appendix/rules.md` 產生 `## 規則對照` 表——`paths:` 命中的 `.claude/rules/` 檔＋沿途的子目錄 `CLAUDE.md`，每份一列、列出它的 `##` 節。逐份讀過再填處置：`套用：§<節> → <片／測試編號>`，或 `不相關：<一句理由>`；套用的節要真的落成矩陣的一列或一支測試。PLAN.md 只留一句「規則對照見 appendix：套用 N 份、不相關 M 份」。checkpoint 前 `scripts/rulesfor.py --check .claude/PRPs/plans/<slug>` 要 exit 0。為什麼：10-17 檢討的 19 條漏網問題裡約 6 條，規則檔早就寫了同樣的規則，只是 PLAN 沒套用。限定範圍的規則要讀到命中的檔才會自動載入，而寫 PLAN 時讀的是正式碼，`.html`／spec 範圍的規則（例如 `a11y.md`、`dom-testing.md`）根本沒載入。結果同一件事到審查才被重新想一次，然後修一次、再走一趟。

## PLAN 審查（大包／高風險包；小包與精簡路不跑）
PLAN 定稿後、checkpoint 之前跑完，owner 一次看 PLAN 與審查結果，不多停一次。為什麼：流出分析裡第 6 階段才抓到的 HIGH，多數「本該攔的閘」是 PLAN——狀態矩陣缺列、先例沒回碼核對、歸類與規則檔矛盾——這三種在 checkpoint 上 owner 看不出來（owner 10-17 定：大包加 PLAN 外審、三方都要）。
1. **路數**：`lane-reviewer` 一顆（內部；沒寫 PLAN、讀得到程式碼與 `.claude/rules/`）＋codex＋grok＋agy，四路同時在背景跑。外審跑不了照 `references/external-review.md` 記「沒跑」、換鏡頭替補。
2. **快照**：`scripts/mkpatch.py --out tmp/<slug>/plan-review`（零改動也照跑，產空 patch 與 baseline）→ `scripts/mkworktree.py --path tmp/<slug>/plan-review/wt-snap --patch tmp/<slug>/plan-review/change.patch --baseline tmp/<slug>/plan-review/baseline.sha256`，SPEC／PLAN 連同 `plan-appendix/` 複製進快照的 `tmp/review-input/`。為什麼不給主樹：grok 有執行能力，快照的免疫力來自沒有人寫它。checkpoint 後 `git worktree remove --force` 移除，第 6 階段另建。
3. **任務書**：填 `assets/plan-review-brief.md` 當共用任務書，「圖給的起點」貼第 4 條寫矩陣時跑的 `affected` 輸出。內部 lane 派工單 `tmp/<slug>/plan-review/tasks/inner.md`、報告 `lane-inner.md`（寫不了檔就 hand-back 全文、主 session 落檔）。外審材料包照 `references/external-review.md`「PLAN 審查的材料包」。
4. **收件**：`scripts/reviewcov.py tmp/<slug>/plan-review` 過 lane 閘。
5. **處置**（主 session）：PLAN.md 末尾加 `## PLAN 審查地圖`，表頭 `| 編號 | 宣稱嚴重度 | 一句話 | 位置 | 來源 | 處置 |`（來源寫 `<lane>#<n>`；R…＝MEDIUM 以上、L…＝LOW）。處置三選一：`改 PLAN（<節或定案>；測試 <編號>）`——預設，編號是第 5 條測試表裡的列，不改行為的（文件、不做清單、片歸屬）寫 `改 PLAN（<節>；無測試：<理由>）`；`不採：<file:line 或規則原句>`——要附程式碼或規則證據，「考慮過」不算；`交 owner`——要推翻 §0 owner 拍板的。HIGH 以上的「改 PLAN」，那支測試的列要寫齊審查提出的反例：初始狀態、觸發的失敗或交錯事件、預期結果、測試層；反例屬於維度表的，改成補維度值、出口或例外列。改完跑 `scripts/reviewcov.py tmp/<slug>/plan-review .claude/PRPs/plans/<slug>/PLAN.md --section "PLAN 審查地圖" --plan-tests` 要 exit 0（點名的編號不在 PLAN 或 `plan-appendix/` 的測試表裡就擋）。為什麼要點名測試：chat-image-publish 的 PLAN 審查已點出「結果不明」那一格、處置也寫了「改 PLAN」，測試卻只測了回讀前就看得到的那格，第 7 階段再修一輪（10-19 檢討）。不另派收斂驗證員：「不採」帶著寫 PLAN 的人的偏誤，所以下一條交給 owner 看。
6. **checkpoint 回報多三項**（第 11 條的 `--check` 不論大小包都要先過）：四路交件狀況（沒跑的寫原因）、採納幾條、HIGH 以上的「不採」逐條白話列出；「交 owner」的條目用 AskUserQuestion 問。

→ Checkpoint（owner 核准 PLAN 才能進第 5 階段）。
