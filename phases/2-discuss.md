# 第 2 階段：討論（方向收斂）

目標：在碰任何細節前，先把**方向、範圍、主方案**定下來。

1. 白話結構化簡報：研究發現、挑戰結論、各方案取捨與推薦（附理由）、矛盾與影響範圍的風險。
2. 與 owner 來回討論。立場規則：有證據支撐的立場要堅持並攤開證據，**被說服才改，不因 owner 堅持就讓步**；owner 的新資訊推翻研究結論時坦白更新。
3. 丟棄式原型（`mattpocock-skills:prototype`；邏輯／狀態問題做單檔可執行程式、UI 問題做多個可切換變體）。**預設跳過**，符合任一條才在方向收斂後、訪談前做：
   - 使用者會直接操作的新互動（新元件、新流程頁），手感要摸到才知道。
   - 新狀態機有讀 SPEC 判斷不了的轉移。
   - owner 與主 session 分歧收斂不了。
   - LLM 輸出品質的問題不在此列，走探針＋盲評（`references/project-deepweave.md`）。
   - 做法：派 subagent 照 skill 做（無專用 agent，用 general-purpose），主 session 只收「題目、變體、怎麼開、owner 要看什麼」，不讀原型碼。同一題的變體由同一顆 agent 做——比的是方案不是做工。
   - **原型碼不進 dev，原型檔留在 `tmp/<slug>/` 當對照**；拍板結果與理由寫進 SPEC「方向決議」。
   - **owner 選定的 UI 原型（含 owner 自己帶來的）預設是交付參照**：版面、元件形狀、選單、動態、操作手感都照做，只有字型與配色照專案色票；第 3 階段展開成差異表（`phases/3-interview.md`）。owner 明說「只取方向」才例外，寫進方向決議。為什麼：journey-scene-layer 把原型當方向、做完 W0–W5 才比出 74 項差異，主 session 又推薦「先做三大件」，owner 10-18：「我發現你省略超多 UI/UX，能不能直接對齊 prototype A」——翻案後再走 6 輪（10-19 檢討，三家外審都排第一）。
4. 收斂標準：每條挑戰結論都有明確處置（採納或駁回，附理由）；方向、範圍、主方案三者確立。
5. 決議寫進 **SPEC.md 首段「方向決議」**：目標、範圍、選定方案與理由、否決方案與理由、已知限制。

研究若無挑戰結論、無替代方案、無矛盾 → 本階段縮成一句確認後直接進訪談。

→ Checkpoint。
