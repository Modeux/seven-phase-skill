# 第 2 階段：討論（方向收斂）

目標：在碰任何細節前，先把**方向、範圍、主方案**定下來。

**簡報前：三取向架構對照（條件觸發）**
- **觸發**：研究結論要新建結構——新模組、新資料表、新狀態機，或跨兩層以上的新流程。**不觸發**：修 bug、研究已找到可照抄的既有模式（第 1 階段 graphify 查到等價物）、owner 在任務描述已指定做法。觸發看任務形狀，**不看主 session 有沒有想到替代方案**：要防的正是寫完 RESEARCH 的 context 錨定在第一個想法、自己想不出真正不同的方案。UI 手感、讀 SPEC 判斷不了的狀態轉移仍走第 3 步原型，兩者不互相取代。
- **派工**：同一則訊息派三顆 `code-architect`，任務書逐字相同（`scripts/extract.py` 摘 RESEARCH 的現況摘要與挑戰結論、附「圖給的起點」，全文路徑列「需要時再讀」），只差一行取向——A 最小改動（最大重用既有模組、不新增抽象）；B 乾淨抽象（邊界清楚、好維護，可以動既有結構）；C 務實折衷（交付速度與長期品質平衡）。研究查過的不重查，只為驗證方案可行去讀碼。
- **交件**：方向級，不寫到函式簽名與建置順序（那是第 4 階段的事）。任務書明寫用這六節取代 agent 定義裡的 Output Format，方便並排：一句話方案、改動面（檔案／模組、正式碼行數量級）、新增的抽象或資料表、重用了什麼、碰到的跨層不變式與 Iron Laws、這個取向放棄了什麼。code-architect 沒有 Write：hand-back 只放這六節全文（≤ 約 60 行，不要摘要），主 session 落檔 `tmp/<slug>/arch/{A,B,C}.md`，第 4 階段列「需要時再讀」。
- **主 session**：並排比較表＋推薦與理由，放進第 1 步簡報；推薦可以是混合方案，寫清楚各取哪部分。三顆大同小異就一句帶過——這本身說明方向明確。owner 用 AskUserQuestion 選（推薦放第一、preview 放各方案的改動面）。
- 成本：10-20 前 30 天 code-architect 平均每顆約 $8，三顆約 $25／包。

1. 白話結構化簡報：研究發現、挑戰結論、各方案取捨與推薦（附理由）、矛盾與影響範圍的風險。
2. 與 owner 來回討論。立場規則：有證據支撐的立場要堅持並攤開證據，**被說服才改，不因 owner 堅持就讓步**；owner 的新資訊推翻研究結論時坦白更新。
3. 丟棄式原型（`mattpocock-skills:prototype`；邏輯／狀態問題做單檔可執行程式、UI 問題做多個可切換變體）。**預設跳過**，符合任一條才在方向收斂後、訪談前做：
   - 使用者會直接操作的新互動（新元件、新流程頁），手感要摸到才知道。
   - 新狀態機有讀 SPEC 判斷不了的轉移。
   - owner 與主 session 分歧收斂不了。
   - LLM 輸出品質的問題不在此列，走探針＋盲評（`references/project-deepweave.md`）。
   - 做法：派 subagent 照 skill 做（無專用 agent，用 general-purpose），主 session 只收「題目、變體、怎麼開、owner 要看什麼」，不讀原型碼。同一題的變體由同一顆 agent 做——比的是方案不是做工。
   - **原型碼不進 dev，原型檔留在 `tmp/<slug>/` 當對照**；拍板結果與理由寫進 SPEC「方向決議」。
   - **owner 選定的 UI 原型（含 owner 自己帶來的）預設是交付參照**：版面、元件形狀、選單、動態、操作手感都照做，只有字型與配色照專案色票；第 3 階段展開成差異表（`phases/3-interview.md`）。owner 明說「只取方向」才例外，寫進方向決議。為什麼：journey-scene-layer 把原型當方向、做完 W0–W5 才比出 74 項差異，主 session 又推薦「先做三大件」，owner 10-18：「我發現你省略超多 UI/UX，能不能直接對齊 prototype A」——翻案後再走 6 輪（10-19 檢討，三家外審都排第一）。
4. 收斂標準：每條挑戰結論都有明確處置（採納或駁回，附理由）；方向、範圍、主方案三者確立。
5. 決議寫進 **SPEC.md 首段「方向決議」**：目標、範圍、選定方案與理由、否決方案與理由（跑了三取向對照的，A／B／C 各一列）、已知限制。

研究若無挑戰結論、無替代方案、無矛盾，**且三取向對照沒觸發** → 本階段縮成一句確認後直接進訪談。

→ Checkpoint。
